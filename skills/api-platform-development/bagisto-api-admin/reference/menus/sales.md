# Sales menu

Everything about an order after (and during) checkout: browsing and managing orders, building an order from the admin side, and the post-order documents an order produces — invoices, shipments, refunds, transactions, bookings. This is the largest admin menu; it mirrors the admin **Sales** sidebar group.

> **Source of truth:** this page gives you the resources, the endpoints, the eligibility rules, and the UX. For the exact request/response body of any call, open its linked api-docs page. **Never invent a payload from memory — open the page and verify the method/fields first.**

**Auth:** every call carries the admin Integration Bearer token (see [connecting-to-the-api](../connecting-to-the-api.md)). Actions are capped by the admin's role — an endpoint the role can't reach returns **403**.

---

## 1. Overview — what Sales manages, and when a row appears

The Sales menu has one **action-bearing** resource and five document resources:

- **Orders** — the heart of the menu. Browse every order, view one in full, and run every per-order action (cancel, comment, invoice, ship, refund). Admins also **build an order for a customer** from here (the Create-Order draft-cart flow — see §3).
- **Invoices, Shipments, Refunds, Transactions, Bookings** — these are **documents an order produces**. A row appears in one of these menus **only once the corresponding document exists** for an order. Placing or paying for an order does not by itself create an invoice/shipment/refund — each must be generated (or auto-generated by store config) from the order first. Transactions are written by payment flows; bookings appear automatically when an order contains a booking product.

**Read-only vs action-bearing:**

| Resource | Surface |
|----------|---------|
| **Orders** | list + detail + per-order **actions** (cancel/comment/invoice/shipment/refund) + Create-Order flow + CSV export |
| **Invoices** | list + detail + print PDF + send-duplicate + mass-update-status + CSV export *(creation is a per-order action under Orders)* |
| **Shipments** | list + detail + CSV export *(creation is a per-order action under Orders)* |
| **Refunds** | list + detail + CSV export *(creation + preview are per-order actions under Orders)* |
| **Transactions** | **read-only** — list + detail + CSV export |
| **Bookings** | **read-only** — list + detail + CSV export |

**Status semantics worth knowing**

- **An invoiced order can still read "pending."** Generating an invoice records *what is owed*, not that it has been *paid*. The invoice (and the order's payment state) flips to `paid` only when a payment transaction is recorded against it. An invoice generated without a captured payment (offline method, no transaction recorded) stays `pending`. Expected, not a defect.
- **Invoice `state` is `paid` / `pending` / `pending_payment` / `overdue`.** The grid normally shows just **Paid** and **Pending**; `pending_payment` displays identically to `pending`. There is **no `refunded` invoice state** — refunds are tracked separately under Refunds.
- **The red "Overdue by N days" line is a derived countdown**, not a stored state. It's `createdAt + payment-term-days` compared to today; the stored `state` stays `pending`. The API returns the raw `state` + `createdAt`, so the client can reproduce the line. `overdue` as a literal stored state is only settable via Mass Update Status (rare).
- **Refund "Refunded Amount"** is the refund's grand total in the store's base currency (subtotal + tax + shipping + adjustment-refund − adjustment-fee), surfaced as `formattedBaseGrandTotal` (raw `baseGrandTotal`) — not just the line-items subtotal.
- **Booking `bookingType`** (`default` / `appointment` / `event` / `rental` / `table`) tells you the kind of booking; the time window comes back as both raw unix timestamps (`from` / `to`) and readable strings (`fromFormatted` / `toFormatted`), all of which can be `null` for non-time-windowed sub-types.

## 2. The list → detail → action pattern

Almost every Sales screen is one of three calls — **list** (`GET …` → `{ data, meta }`), **detail** (`GET …/{id}` → full record with relations embedded), **action** (`POST/PUT/DELETE`). The full pattern, the `{ data, meta }` envelope, pagination (`?page=` / `?per_page=`), permissions, and the error table live in [connecting-to-the-api](../connecting-to-the-api.md) — don't re-implement them per screen. Detail payloads **embed** what the screen needs (items, addresses, the order context), so you rarely chain follow-up GETs.

### Order lifecycle — which action, in what order, and its gate

Once an order exists, it moves through a lifecycle. Each action has a prerequisite and **refuses with a clear error when it isn't met**:

1. **Invoice — record payment.** Records that payment was collected for some or all items. You can invoice part now and the rest later. **Not available for `paypal_standard` orders** (captured by the gateway, not the admin). An order generally can't be refunded until it's been invoiced.
2. **Ship — fulfil.** Marks items dispatched and records carrier + tracking. Needs items still awaiting shipment **and** enough stock at the chosen inventory source. Partial shipments allowed.
3. **Refund — return money.** Returns money for invoiced items and/or an adjustment. Call **Refund Preview first** to compute totals without writing. Requires something left to refund (an un-refunded invoiced amount or a returnable quantity).
4. **Cancel — abandon early.** Only possible while there's still something to cancel (nothing fully invoiced or shipped). A **closed or fraud-flagged** order can't be cancelled.
5. **Comments — any time.** Work at any stage; set `customerNotified` to email the customer the note. No permission gate.

A typical fulfilled order runs **Create → Invoice → Ship** (then an optional **Refund**); an abandoned one runs **Create → Cancel**. Each action's permission key gates it (`sales.orders.cancel`, `sales.invoices.create`, `sales.shipments.create`, `sales.refunds.create`); a role without it returns **403**.

## 4. Invoices

Store-wide list of every generated invoice, plus single-invoice actions. A row exists only after an invoice has been **generated** for an order.

| Operation | REST | GraphQL field |
|-----------|------|---------------|
| List invoices | `GET /api/admin/invoices` | `adminInvoices` |
| Invoice detail | `GET /api/admin/invoices/{id}` | `adminInvoice` |
| Print invoice (PDF) | `GET /api/admin/invoices/{id}/print` | *(REST-only binary)* |
| Send duplicate invoice | `POST /api/admin/invoices/{id}/send-duplicate` | `createAdminInvoiceSendDuplicate` |
| Mass update status | `POST /api/admin/invoices/mass-update-status` | `createAdminInvoiceMassUpdateStatus` |
| Export (CSV) | `GET /api/admin/invoices/export` | *(REST-only)* |

Docs: [list](https://api-docs.bagisto.com/api/rest-api/admin/sales/invoices/list), [detail](https://api-docs.bagisto.com/api/rest-api/admin/sales/orders/get-invoice), [print](https://api-docs.bagisto.com/api/rest-api/admin/sales/orders/print-invoice), [send duplicate](https://api-docs.bagisto.com/api/rest-api/admin/sales/orders/send-duplicate-invoice), [mass update status](https://api-docs.bagisto.com/api/rest-api/admin/sales/invoices/mass-update-status), [export](https://api-docs.bagisto.com/api/rest-api/admin/sales/invoices/export).

- **Invoice creation is NOT here** — it's a per-order action (§3). This menu only lists + acts on existing invoices.
- **Print** returns a binary `application/pdf` attachment — no GraphQL counterpart. Send `Accept: application/pdf`.
- **Send Duplicate** re-sends the invoice email; you can override the recipient, otherwise it goes to the order's customer email. It re-delivers a copy without regenerating the invoice.
- **Mass Update Status** is a **manual flag only** (`pending` / `paid` / `overdue`) — it does **not** capture or reverse a payment and creates no transaction. Use it to correct or annotate state, not to take money.

## 9. UI / UX

### Data grids (list screens)

Each list is a paginated table over the `{ data, meta }` envelope. Drive it with `?page=` / `?per_page=` (default 10, cap 50) + the screen's filters. Filters are **AND**-combined (more filters = more restrictive); each list's docs page declares its exact filter set.

- **Orders** — the richest grid. Columns: ID, status (+ label), channel, customer, email, grand total, order date. Filters: `status` (`pending` / `pending_payment` / `processing` / `completed` / `canceled` / `closed` / `fraud`), `grand_total` (+ `grand_total_from` / `_to`), `channel`, `customer` (partial), `email` (partial), `date_range` preset (`today`, `yesterday`, `this_week`, `this_month`, `last_month`, `last_three_months`, `last_six_months`, `this_year`) **or** custom `date_from` / `date_to` (the custom range overrides the preset). Sort: `sort` + `order` (default `created_at desc`).
- **Invoices** — filter by state and order/invoice number; the grid shows the **Paid / Pending** badge and the derived "N days left / Overdue by N days" countdown line under pending rows. Reproduce the countdown from `createdAt + payment-term-days`.
- **Shipments / Refunds / Transactions / Bookings** — narrower grids; consult each list docs page for the available filters and columns. Bookings surface `bookingType` and the from/to window (raw unix + formatted).

Each grid's filter set is what the API exposes — don't add filters the docs don't list.

### Mass-actions

- **Invoices → Mass Update Status** (`POST /api/admin/invoices/mass-update-status`) is the only Sales mass-action. Send the selected invoice ids + the target status (`pending` / `paid` / `overdue`). It's a manual flag, not a payment capture (§4). The other Sales resources have **no** mass-actions.

### Detail views

Open a row → the detail payload inlines everything the screen needs (no follow-up GETs). Order detail embeds customer, both addresses, type-aware items, and the generated documents. Invoice/shipment/refund detail embed the order/customer context, addresses, and line items. Booking detail embeds the order's addresses, payment/shipping info, and document arrays.

### Action modals + eligibility (Orders)

Build each per-order action as a modal launched from the order detail, and **disable / hide actions the order isn't eligible for** so the user never hits a wasted 4xx:

| Action | Eligibility rule | Ineligible → |
|--------|------------------|--------------|
| **Cancel** | Something still cancellable (nothing fully invoiced/shipped); not closed/fraud | 422 with a reason (closed / fraud / nothing-to-cancel) |
| **Create Invoice** | Items left to invoice; payment method **not** `paypal_standard`; not closed/fraud | 422 (closed / fraud / paypal-standard-blocked / nothing-to-invoice) |
| **Create Shipment** | Items left to ship + enough stock at the chosen source; not closed/fraud | 422 (closed / fraud / nothing-to-ship / insufficient stock) |
| **Create Refund** | An un-refunded invoiced amount or returnable qty; not closed/fraud | 422 (closed / fraud / nothing-to-refund / amount-exceeds-max) |
| **Comment** | Always available | — |

For the **invoice / shipment / refund** modals, render a per-item quantity input bounded by the item's remaining-to-invoice / -ship / -refund quantity, and use **Refund Preview** to live-update the computed totals as the admin changes quantities/adjustments before committing. A `403` on any action means the role lacks that action's permission — surface "you don't have permission for this action," not a generic error.

### CSV export buttons

Every Sales grid has an **Export** button → a REST-only `GET …/export` that streams a `text/csv` attachment honouring the grid's current filters. **Send `Accept: text/csv`** (a default `Accept: application/json` returns 406). No GraphQL counterpart — binary streams aren't expressible over GraphQL; the same is true for invoice **Print PDF**.

### Mobile

Single-column tables that collapse to stacked cards; sticky action bar on the order detail; keep the status badge + grand total visible at the top of each card. Action modals full-screen on small viewports.

## 10. Errors

Standard admin statuses (full table in [connecting-to-the-api](../connecting-to-the-api.md)):

| Status | When | Handle by |
|--------|------|-----------|
| **401** | Missing / expired / revoked admin token | Re-issue the token in the panel |
| **403** | Role lacks the action's permission (e.g. `sales.invoices.create`) | "You don't have permission for this action" |
| **404** | Unknown order / invoice / shipment / refund / transaction / booking id | — |
| **409** | Wrong-step in the Create-Order draft-cart sequence | Send the user to the missing prerequisite (see create-order flow) |
| **422** | Ineligible action (closed/fraud, nothing-to-invoice/ship/refund, paypal-standard-blocked, insufficient stock, amount-exceeds-max) or invalid input | Inline eligibility/field message; keep the modal open |

## 11. Checklist

**List screens**
- [ ] Each grid driven by `?page=` / `?per_page=` over `{ data, meta }`; only the documented filters exposed; AND-combination understood.
- [ ] Orders grid wires status / grand_total(+range) / channel / customer / email / date_range-or-custom / sort filters.
- [ ] Invoice grid reproduces the **Paid/Pending** badge + derived overdue countdown from `state` + `createdAt`.
- [ ] Bookings grid surfaces `bookingType` + from/to (raw unix + formatted), handling `null` windows.

**Detail screens**
- [ ] Detail payload's embedded relations rendered without follow-up GETs (order: customer/addresses/items/documents; booking: order context + documents).

**Orders — actions & eligibility (CRITICAL)**
- [ ] Cancel / Invoice / Shipment / Refund actions **gated on eligibility** (hide/disable when ineligible); 422 reasons surfaced inline.
- [ ] Invoice action hidden for `paypal_standard` orders.
- [ ] Invoice/shipment/refund modals bound per-item quantity to the remaining-to-X quantity.
- [ ] **Refund Preview** called to live-compute totals before Create Refund commits.
- [ ] Comments (list + add) wired; `customerNotified` toggle emails the customer.
- [ ] 403 on any action shows a permission message, not a generic error.

**Documents are order-produced (CRITICAL)**
- [ ] Invoice/Shipment/Refund **creation runs against the order** (§3), not from their own menus; those menus list + view (+ invoice print/send-duplicate/mass-status) only.
- [ ] Transactions + Bookings treated as **read-only** (no create/edit UI).
- [ ] "Row appears only after the document exists" reflected in the UI (empty states, not errors).

**Exports & binaries**
- [ ] Every grid's Export button hits `GET …/export` with `Accept: text/csv`; filters carried through.
- [ ] Invoice Print PDF requested with `Accept: application/pdf`; both are REST-only (no GraphQL).

**Create-Order**
- [ ] The admin Create-Order flow built per [../flows/create-order.md](../flows/create-order.md) (not duplicated here).

**Both transports**
- [ ] Admin Bearer token on every call; GraphQL action mutations select **result fields** (not a generic `id`), inputs camelCase, list queries use cursor pagination — see [../graphql.md](../graphql.md).
